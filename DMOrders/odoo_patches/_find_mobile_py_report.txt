2. CONCLUSION EJECUTIVA (como llega data a la tablet)
-----------------------------------------------------
Hay DOS caminos posibles en Odoo hacia apps moviles:

A) JSON-RPC estandar Odoo (call_kw -> search_read / search_count / create / write)
   - HubManager/DMOrders (contexto previo) usa call_kw sobre modelos estandar
     (res.partner, sale.order, etc.) via wrappers tipo HubResPartner.
   - En ese camino, NO hace falta un controller custom para el PULL:
     Odoo core sirve search_read. Los .py custom solo PARTICIPAN porque
     EXTENDEN los modelos (anaden campos como misc_estado, mobile_sync,
     use_mobile_app, id_referencia) que el cliente puede pedir en "fields".

B) Controllers HTTP custom del modulo mnsa_mobile (/connect/*, /apiped/*)
   - Endpoints dedicados que serializan partners, journals, invoices,
     catalogo, stock, etc. con search / search_read internos.
   - Estos SI son codigo Python que "sirve" datos a apps moviles
     (cobranzas / pedidos), independientemente de call_kw.

Para DMOrders tablet orientado a JSON-RPC: el pull es mayormente call_kw
estandar; los .py listados abajo aportan el ESQUEMA/CAMPOS y, en push,
logica al crear sale.order con mobile_sync/id_referencia.

5. SOBRE search_read DE PARTNERS
-------------------------------
Controllers custom que envuelven search_read/search de res.partner:
  1) mnsa_mobile/controllers/cobranzas_mobile_api.py -> get_res_partner
  2) mnsa_mobile/controllers/mngsa_mobile_pedido_api.py -> obtenerClientes
  3) mnsa_mobile/controllers/request_account_move.py -> get_res_partner_deprecated

Si DMOrders usa unicamente JSON-RPC call_kw("res.partner","search_read",...),
entonces esos controllers NO se invocan; Odoo core atiende la peticion y
los campos custom vienen de m2_res_partner_model.py + mnsa_base partner extends.

7. VEREDICTO
------------
- El modulo custom que concentra la app movil es personalized/mnsa_mobile.
- No existe un modulo "DMOrders" en Odoo; dmorder/dm_order no aparecen en .py.
- base/sale (mic2_sale) aporta extensiones generales de sale.order, no sync tablet.
- Si la tablet HubManager hace pull con JSON-RPC call_kw search_read/search_count,
  el "serving" es el ORM/JSON-RPC de Odoo core; los .py anteriores solo aportan
  campos/extends y (en create) logica cuando mobile_sync + id_referencia.
- Los controllers /connect/* y /apiped/* son el camino HTTP alternativo/legacy
  para cobranzas y pedidos moviles (search_read embebido de partners y maestros).
